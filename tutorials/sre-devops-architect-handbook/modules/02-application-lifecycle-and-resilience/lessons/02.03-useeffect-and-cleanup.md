### 1. Real-world analogy

### Restaurant workflow

- **Customer:** asks for a meal → an authenticated user requests a Todo operation.
- **Waiter:** accepts the request → React and the FastAPI route accept and validate the Todo request.
- **Order board:** records pending work → the request or state handoff (not necessarily a message queue).
- **Chef:** performs the work → the Todo service and repository execute the operation.
- **Kitchen records:** retain the result → SQLite stores authoritative Todo data.
- **Manager:** checks quality and failures → tests, CI, metrics, logs, and operational checks.

### 3. Beginner lab — observe the mechanism

> **Evidence rule:** A model of a related concept is not a demonstration of **useeffect and cleanup**. If the script below does not exercise the named mechanism directly, treat it as a prerequisite only and complete the technology-specific labs linked from the module index.


**Purpose:** Run a minimal standard-library Python model related to **retry budget and backoff**. This script does not modify Todo, install services, or need credentials.

#### Complete code (copy into a terminal)

```bash
python3 - <<'PY'
attempts = 4
for attempt in range(1, attempts + 1):
    delay = min(2 ** (attempt - 1), 8)
    print(f"attempt={attempt} next_backoff_seconds={delay}")
print("note: add jitter and an overall deadline in production")
PY
```

#### Expected output

```text
attempt=1 next_backoff_seconds=1
attempt=2 next_backoff_seconds=2
attempt=3 next_backoff_seconds=4
attempt=4 next_backoff_seconds=8
note: add jitter and an overall deadline in production
```

#### What each result means

Retries need an idempotency decision, bounded attempts, jitter, and a deadline. The exact expected output above is from the deterministic model; compare it with your terminal before making any conclusion.

### 6. Architect lab — failure, trade-offs, and design review

#### Failure hypothesis

Assume the component responsible for **useeffect and cleanup** is unavailable or behaves unexpectedly while a user completes a Todo. Do not inject a failure into the real application. Describe the dependency boundary and whether the user action should succeed, fail, or degrade.

#### Three design options

| Option | Benefit | Cost / risk |
|---|---|---|
| Keep existing Todo design | Fewer dependencies; easier local operation | May not meet a new nonfunctional requirement |
| Add the smallest mechanism for **useeffect and cleanup** | Targeted capability and measurable experiment | New failure paths and maintenance |
| Adopt a managed or distributed alternative | Potentially better scale/availability | Operational cost, complexity, vendor/lock-in considerations |

#### Architect decision task

Write a 5–8 sentence mini-ADR: **Context → requirements → options → decision → consequences → rollback**. Include one measurable acceptance criterion (e.g. user-visible success, latency, data durability, recovery time, or authorization correctness). Name the specific Todo file or component affected. No actual deployment is required.

#### What to observe and how to verify

- **Healthy path:** define an end-user Todo action and the evidence of success.
- **Failure path:** distinguish error symptom from underlying cause; name the blast radius.
- **Recovery:** define an observable recovery criterion and a safe rollback.
- **Security:** identify any new identity, secret, or network boundary.
- **Cost:** justify the added operational burden against the current SQLite-first design.
