## 1. Real-world analogy

Think of a **restaurant**:

- **Customer** requests food (a Todo is completed).
- **Waiter = producer** places an order on the board using `put()`.
- **Order board = queue** holds pending orders.
- **Chef = consumer** takes an order using `get()` and prepares it using application code.
- **Completion marker = `task_done()`** records that one retrieved task is finished; it does **not** remove the item (that already happened at `get()`).

```text
Customer -> Waiter (producer) --put()--> [Order board / Queue]
                                            |
                                           get()
                                            v
                                        Chef (consumer)
                                            |
                                     process message
                                            |
                                       task_done()
```

The waiter can accept another order while the chef is busy **once the producer and consumer run concurrently**. A single-thread demonstration does not yet provide this concurrency.

## 2. Understanding `queue.Queue`

`queue.Queue` is a **thread-safe, in-memory FIFO queue**. It is useful for learning and for coordinating threads inside one process. It is **not durable storage**.

| Operation | Meaning | Important detail |
|---|---|---|
| `Queue()` | Create an empty queue | Exists only in process memory |
| `put(item)` | Enqueue an item | Can block if a bounded queue is full |
| `get()` | Dequeue an item | **Blocks** on an empty queue by default; does not execute the item |
| `get(timeout=2)` | Wait at most two seconds | Raises `queue.Empty` if no item arrives |
| `qsize()` | Approximate queued item count | Not reliable for synchronization between threads |
| `empty()` | Approximate empty check | Do not use as a concurrent worker termination condition |
| `task_done()` | Decrease unfinished-task count | Does not dequeue; does not persist an acknowledgment |
| `join()` | Wait until all enqueued tasks have matching `task_done()` calls | Can wait indefinitely if tasks are never marked done |

**Worked example:** `put('TodoCompleted-1')` increases queue size to one. `get()` returns that string and decreases queue size to zero. Your consumer then processes the string and calls `task_done()`. The queue has no built-in Slack notification implementation: processing is your code.

**Failure boundary:** If the process stops, pending messages disappear. If processing fails after `get()`, the item is already dequeued; `task_done()` is accounting, not a broker redelivery mechanism.

## Lab 2 — Producer, queue, consumer (single thread)

Run from any directory:

```bash
python3 - <<'PYCODE'
from queue import Queue
q = Queue()  # Empty restaurant order board.
for number in range(1, 4):
    q.put(f'TodoCompleted-{number}')  # Waiter adds an order.
    print('PRODUCER queued:', number)
print('WAITING:', q.qsize())  # Expected: 3.
while not q.empty():  # Only safe for this single-thread demonstration.
    message = q.get()  # Chef picks up an order; item is removed here.
    print('CONSUMER processed:', message)  # Simulated work.
    q.task_done()  # Record completion, NOT removal.
q.join()  # Wait for all unfinished-task accounting to reach zero.
print('WAITING AFTER:', q.qsize())  # Expected: 0.
PYCODE
```

**Expected:** Three `PRODUCER` lines, `WAITING: 3`, three `CONSUMER` lines, `WAITING AFTER: 0`.

## Lab 3 — Empty queue: blocking and timeout

```bash
python3 - <<'PYCODE'
from queue import Queue, Empty
q = Queue()
print('Waiting for work for up to 2 seconds...')
try:
    q.get(timeout=2)
except Empty:
    print('EXPECTED: Empty exception, not None')
PYCODE
```

**Expected:** After roughly two seconds, `EXPECTED: Empty exception, not None`. Without `timeout`, `get()` waits indefinitely. In production, workers need shutdown and cancellation handling.

## Lab 4 — `get()` versus `task_done()` versus `join()`

```bash
python3 - <<'PYCODE'
from queue import Queue
q = Queue()
q.put('Send Slack')
print('BEFORE GET:', q.qsize())  # 1.
message = q.get()
print('AFTER GET:', q.qsize())  # 0: get() removed the message.
print('PROCESS:', message)
q.task_done()  # Acknowledge processing to this in-memory queue.
q.join()  # Returns only because task_done() was called.
print('JOIN RETURNED')
PYCODE
```

**Failure thought experiment:** If an exception occurs after `get()` but before `task_done()`, the message is removed, yet `join()` can block forever. Do not intentionally run an unbounded `join()` to prove it.

## Lab 5 — Producer and consumer concurrently (threads)

```bash
python3 - <<'PYCODE'
from queue import Queue
from threading import Thread
from time import sleep
q = Queue()

def consumer():
    while True:
        item = q.get()  # Wait until work arrives.
        try:
            if item is None:  # Sentinel signals clean shutdown.
                return
            print('CONSUMER working:', item)
            sleep(0.1)  # Simulated I/O, not real Slack.
        finally:
            q.task_done()

worker = Thread(target=consumer)
worker.start()
for n in range(3):
    q.put(f'TodoCompleted-{n}')
    print('PRODUCER queued:', n)
q.put(None)  # One sentinel for this one worker.
q.join()
worker.join()
print('ALL WORKERS STOPPED')
PYCODE
```

**Expected:** Three produced and consumed messages and `ALL WORKERS STOPPED`. Print ordering may interleave; the worker runs concurrently.

## Lab 6 — Failure and in-memory retry

```bash
python3 - <<'PYCODE'
from queue import Queue
q = Queue()
q.put('Send Slack')
message = q.get()
try:
    raise ConnectionError('simulated Slack outage')
except ConnectionError as error:
    print('EXPECTED FAILURE:', error)
    q.put(message)  # Teaching-only retry; may duplicate side effects.
finally:
    q.task_done()  # Account for original attempt.
retry = q.get()
print('RETRY:', retry)
q.task_done()
q.join()
PYCODE
```

**Expected:** Simulated outage, then `RETRY: Send Slack`. **Caution:** In-memory retries are not durable; real systems need bounded retries, backoff, poison-message handling, and idempotency.

## Lab 7 — Volatile queue and simulated restart

```bash
python3 - <<'PYCODE'
from queue import Queue
q = Queue()
q.put('Pending notification')
print('BEFORE:', q.qsize())  # 1.
q = Queue()  # Replace memory: models a process restart.
print('AFTER:', q.qsize())  # 0.
PYCODE
```

**Expected:** `BEFORE: 1`, `AFTER: 0`. This is why reliable notifications may require a SQLite transactional outbox or durable message broker.

## SRE/DevOps perspective

A producer delivering 100 messages/second with a consumer handling 60 messages/second accumulates **40 messages/second**, or **2,400 messages in a minute**. Monitor queue depth, oldest-message age, processing latency, retries and errors. `queue.Queue` is thread-safe in one process, not a durable distributed broker.
