## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: No dependencies - can start immediately
- **Foundational (Phase 2)**: Depends on Setup completion - BLOCKS all user stories
- **User Stories (Phase 3+)**: All depend on Foundational phase completion
  - User stories can then proceed in parallel (if staffed)
  - Or sequentially in priority order (P1 → P2 → P3)
- **Priority (Phase 10)**: Depends on Phases 1–9. Tests T064–T077 fail before T078–T085
- **Polish (Final Phase)**: Depends on all desired user stories being complete. T086 depends on Phase 10

### User Story Dependencies

- **User Story 1 (P1)**: Can start after Foundational (Phase 2) - No dependencies on other stories
- **User Story 2 (P1)**: Can start after Foundational - Uses the todo created in US1 when demonstrated together, and is testable with repository fixtures alone
- **User Story 3 (P1)**: Can start after Foundational - Needs an owned todo fixture, not a completed US2
- **User Story 4 (P2)**: Can start after Foundational - Read of an owned todo; no dependency on update or delete
- **User Story 5 (P2)**: Can start after Foundational - Partial update does not require complete or delete
- **User Story 7 (P2)**: Depends on the completion-update repository capability from User Story 3 (T031). Tests may create a completed row directly and do not need the US3 route. Do not duplicate that repository method
- **User Story 6 (P3)**: Can start after Foundational - Delete is testable with a created row and does not require incomplete
- **Priority (Phase 10)**: Starts after the completed stories. US1 storage and response (T078–T081) come before US5 update (T082–T085). US2, US3, US4, and US7 tests assert the shared response and the untouched priority column; they do not add a second write path

### Within Each User Story

- Tests MUST be written and FAIL before implementation
- Schemas before services
- Repository methods before service methods
- Service methods before route handlers
- Story complete before moving to the next priority

### Parallel Opportunities

## Implementation Strategy

### MVP First (User Story 1 Only)

1. Complete Phase 1: Setup
2. Complete Phase 2: Foundational (CRITICAL - blocks all stories)
3. Complete Phase 3: User Story 1
4. **STOP and VALIDATE**: Test User Story 1 independently
5. Demo create with an identified caller

### Incremental Delivery

1. Complete Setup + Foundational → identity and empty schema ready
2. Add User Story 1 → create todos (MVP)
3. Add User Story 2 → list the caller's todos
4. Add User Story 3 → mark completed
5. Add User Story 4 → retrieve by id
6. Add User Story 5 → update title and description
7. Add User Story 7 → mark incomplete
8. Add User Story 6 → permanent delete
9. Add Phase 10 → priority on create, response, and partial update
10. Each story adds value without breaking previous stories

### Parallel Team Strategy

With multiple developers:

1. Team completes Setup + Foundational together
2. Once Foundational is done:
   - Developer A: User Story 1
   - Developer B: User Story 2
   - Developer C: User Story 4
3. Stories complete and integrate independently. Stories that share `todo_repository.py`, `todo_service.py`, and `api/routes/todos.py` should land those edits one story at a time

- Stop at any checkpoint to validate story independently
