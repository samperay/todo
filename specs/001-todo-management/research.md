# Research: Basic Todo Management

## Runtime stack

- **Decision**: Python 3.12 or newer, FastAPI, Pydantic v2, SQLAlchemy 2.x, SQLite for local development and default tests, and pytest. No Alembic.
- **Rationale**: Constitution 3.0.0 makes SQLite the local and default test database and allows `metadata.create_all()` during initial development. Alembic and a mandatory PostgreSQL engine were removed from the stack. PostgreSQL may be introduced later by changing the database URL only.
- **Alternatives considered**: Keeping Alembic was rejected because this phase does not require migrations. A sync engine was rejected because aiosqlite provides an async interface and the constitution requires async I/O when the library supports it.

## Process layout

- **Decision**: One backend package, `todo_api`, with API, service, repository, and database layers. FastAPI `Depends` injects the current person and the todo service. Route functions validate through Pydantic, call one service method, and return a Pydantic response.
- **Rationale**: The constitution forbids business rules and SQL in handlers, and forbids handlers constructing their own collaborators when an injectable boundary exists.
- **Alternatives considered**: A single module that queries from the route was rejected. Putting Pydantic models on SQLAlchemy classes was rejected so the API schema can omit `owner_id`.

## Identity

- **Decision**: A person is a row created by `POST /api/v1/users`. The response includes the person id and a random token shown once. Later calls send `Authorization: Bearer <token>`. The database stores only a hash of the token. The API dependency resolves the person and passes the person id into the service. A missing or unknown token is 401 with the shared error schema and the message that the caller must be identified. No password, role, or login endpoint is added.
- **Rationale**: The spec requires a stable identity and rejects unidentified callers, and it leaves the proof mechanism to planning. A one-time token is enough for "the same person when they return" without a second account-management feature. Hashing the token keeps the credential out of the database and out of logs.
- **Alternatives considered**: A client-supplied user id header was rejected because anyone could impersonate another person. Email and password registration was rejected as extra scope. Full OAuth was rejected for the same reason.

## HTTP resources

- **Decision**:
  - `POST /api/v1/users` creates an identity.
  - `POST /api/v1/todos` creates a todo (201).
  - `GET /api/v1/todos` lists the caller's todos, newest `created_at` first, then id for a stable tie-break.
  - `GET /api/v1/todos/{id}` retrieves one owned todo.
  - `PATCH /api/v1/todos/{id}` changes title, description, or both.
  - `POST /api/v1/todos/{id}/complete` marks it completed.
  - `POST /api/v1/todos/{id}/incomplete` marks it incomplete.
  - `DELETE /api/v1/todos/{id}` returns 204. A second delete returns 404.
- **Rationale**: Update is partial, so PATCH matches the intent. Completion is a separate action from text update, so it is not a field on PATCH. The spec forbids changing `completed` through update.
- **Alternatives considered**: `PATCH` with `completed: true` was rejected because it mixes the completion action into text update. `PUT` was rejected because omitted fields must stay unchanged.

## Identifiers and time

- **Decision**: Todo and person ids are UUID values generated by the service. Clients cannot send an id. Deleted ids are not reused. `created_at` and `updated_at` are timezone-aware UTC timestamps. JSON uses ISO-8601. On create they are equal. `updated_at` changes only when title, description, or completed actually changes.
- **Rationale**: UUIDs satisfy stable identity without reuse. UTC timestamps are comparable across clients. The spec left display formatting to planning.
- **Alternatives considered**: Database sequences were rejected because they are easier to guess and are not required. Naive local timestamps were rejected because ordering and comparison then depend on the server zone.

## Validation and errors

- **Decision**: Title and description limits are Pydantic validators: title is required, must contain a non-whitespace character, and is at most 200 characters; description is optional, empty or whitespace-only becomes "no description" (`null` in JSON and the database), and is at most 2,000 characters. Those failures return FastAPI's 422 validation body. Request models forbid extra fields, including `completed`, `id`, and `owner_id`. Domain misses raise `TodoNotFound` in the service. The API layer maps that to 404 `{ "error": { "code": "not_found", "message": "Todo not found" } }`. The same body is used for an id owned by someone else. 401 uses `{ "error": { "code": "unauthenticated", "message": "You must be identified." } }`.
- **Rationale**: The constitution says validation keeps the framework format, and domain errors use one schema translated at the API boundary. Identical not-found text avoids revealing another person's todo.
- **Alternatives considered**: A custom 400 body for title length was rejected because it would fork validation away from the framework format. HTTP 403 for another owner's id was rejected because the spec says to report that the todo does not exist.

## Last committed write wins

- **Decision**: No version column, ETag, or 409 response. Each write runs in one repository transaction and updates only the columns that request sets. The later committed transaction wins for those columns. The service does not lock rows and does not call engine-specific SQL. The caller is not told that another change overlapped. A write whose row is already gone raises `TodoNotFound` and does not insert a replacement.
- **Rationale**: The spec says the later change replaces the earlier one and the person is not warned. The concrete overlap example sends both title and description in the later update, so that commit overwrites the earlier title. Partial update still applies: a request that omits description does not write that column (FR-012). SQLite serializes writers; a portable transaction is enough and does not depend on a row-lock dialect.
- **Alternatives considered**: Optimistic concurrency was rejected because a rejected second save is the option the spec did not choose. `SELECT FOR UPDATE` was rejected because it is engine-specific and would leak into persistence behavior the service must not depend on. Field-by-field merge of two stale snapshots was rejected.

## Database access

- **Decision**: The app uses SQLAlchemy asyncio. The default URL is `sqlite+aiosqlite:///./todo.db`, a non-secret local file. `DATABASE_URL` may override it. On startup, database infrastructure runs `Base.metadata.create_all()` through the async engine (`run_sync`). That call is not in a route or a service. Repositories are the only modules that query or commit. Ids use a portable SQLAlchemy UUID mapping. Timestamps are UTC values written by the application, not by engine date functions. Switching engines later is a URL change plus a repository check, not a service or API change.
- **Rationale**: Constitution VI requires SQLite locally, a configurable URL, repository isolation, and no SQLite-specific business rules. `create_all` is the allowed schema initializer for this phase. A file URL default needs no committed credential.
- **Alternatives considered**: Alembic was rejected for this phase. PostgreSQL as a required local database was rejected. Putting `create_all` in a route or service was rejected because schema and driver details must stay in infrastructure. An in-memory SQLite default for the running app was rejected because a process restart would drop the person's todos, which the spec says remain until delete.

## Tests

- **Decision**: Unit tests call the service with an in-memory repository double and cover ownership, no-op complete and incomplete, and not-found. Repository and API tests use a temporary SQLite file, call the same `create_all` initializer, and never require PostgreSQL. API tests use HTTPX and cover 201, 200, 204, 401, 404, and 422, including two callers.
- **Rationale**: The constitution requires pytest, service tests that can substitute the repository, repository tests on the configured database, and SQLite as the default test database.
- **Alternatives considered**: API-only tests were rejected because service rules would then be tied to HTTP. A PostgreSQL test requirement was rejected by constitution 3.0.0.
